# Round9独立監査と、ポケモン提出物から導くハイブリッド設計

作成日：2026-09-23。対象はユーザー提供のRound9 ZIPと `grimmsnarl_ml_vfinal_submission.tar.gz`。本稿の「今回確認」は保存物の静的解析・再集計・保存重みの推論を指す。新規学習、新規ゲーム実行、Kaggle提出、ポケモン対戦実行は行っていない。

## 1. 結論

ユーザーの「全判断を学習モデルへ任せず、得意な判断をモデルに、確実な処理をロジックに任せる」という方向は、今回のコード比較と整合する。ただし、単にルールを増やすのではなく、**何の候補を、どの条件で、誰が選び、その仕事を誰が最後まで実行するか**を明確にする必要がある。

次の競技用の主軸は、弱いA2へ救済ルールを追加することではなく、**強い既存方策を基準として保持し、実行可能なタスク候補の選択を学習で改善する構成**とすることを提案する。A2の純粋学習改善は別の比較実験として残す。純粋学習の研究上の成功と、ハイブリッド全体の競技上の成功を混同しない。

特に重要な発見は四つある。

1. 評価されたA2は、生のモデル出力を無加工で実行する方式ではない。しかし、合法性・共有資源処理はあっても、戦略的タスク管理の介入は記録上ゼロだった。
2. actor token全体の83.27%に対し、移動方向の一致率は28.87%、SELLの一致率は29.54%だった。全体accuracyだけでは運搬・販売・経済循環の弱さを見落とす。
3. 64試合のA2は行動の87.99%が移動で、day=20に48/64試合が作物も家畜もゼロになっている。終局の売り残しだけでは説明できない、途中の生産能力の崩壊である。
4. **ポケモン最終版の探索は既定でOFFである。** 有効な設計は「学習候補ランキング＋対応場面の選別＋限定的補正＋ルール代替」であり、「探索なら学習より良い」という設計ではない。

根拠の入口：`evidence/EVIDENCE_INDEX_JA.md`、`evidence/POKEMON_CODE_EVIDENCE.md`。

## 2. 監査範囲と、今回の添付に不足しているもの

ZIPは746ファイルを含む実験ディレクトリの書き出しだった。内部の `bundles/complete_v2_contents.json` は別の完全版バンドルを記述しており、その一覧にある864ファイルのうち、対応する相対パスで740ファイルを確認、124ファイルは今回のZIPに存在しなかった。これは「添付そのものが破損している」との判定ではなく、**添付の実体と、同梱された完全版一覧の範囲が違う**という指摘である。

今回の実体には、A0の展開済みソース、A2の保存重み・特徴配列・学習記録・176保存対戦・診断ログなどがある。一方、**最終A2のruntime/main/spatial_policy等、最終v3提出tar、v122/v124のtar、固定engine本体、完全な元教師リプレイ、学習・検証スクリプトの一部はない**。

したがって、最終A2の内部処理の全行監査や、固定engineによる再対戦は今回できていない。A2の実行構成については、旧ソース、実装報告、実際の評価トレースを区別した。ポケモン側のソースは添付から直接読めた。

独立確認した範囲は以下である。

- 176保存対戦のreplay/diagnostic SHA-256、seed、記録数、DONE/DONE、終局資金、CSV記録との一致。176/176で整合した。ただし同条件の版比較を含み、176独立条件ではない。
- A2主学習2 seed×4 headの初期・最終重みhashと変化。8 headすべて宣言hashと一致し、初期と最終は異なった。
- 選択seed 20260924のactor token 16,692行、market token 6,714行、計23,406行を独立NumPy実装で再推論。保存confusion matrixと完全一致した。
- 最終64試合の状態スナップショット、行動種別、逆戻り移動、診断トレース、プラン介入、モデルraw→mask変化を再集計した。
- A2 v2/v3の共通8試合について、所要時間関係のフィールドを除く全action・observation・state・rewardの意味的な一致を確認した。

v3の実ゲーム証拠は8試合、64試合はv2である。v3を「64試合再検証済み」とは扱わない。v123は今回の評価相手に含まれない。

## 4. A2は「モデルだけ」なのか

評価トレースから確認できる構成は、概ね次のとおりである。

```
現在の観測・そのターンに受理された先行行動
    → actor/market/quantityの学習予測
    → 実行可能な候補への制限
    → 共有資金・在庫・種・数量・順序の台帳処理
    → 最終action
```

最終64試合の46,016判断では、`plan.disabled=true` が46,016件、activeは0、interventionsも0、`final_action == ledger_action` が全件だった。actorのraw top-1が合法候補外で、mask後に別tokenとなった例は103,922/306,692、33.89%である。したがって、文字どおり「生のモデル出力だけ」ではない。

しかし、これは基本的に**実行可能性を保つ層**である。「現在の農場では給餌を優先すべき」「運搬タスクを完了するまで別仕事へ移らない」「今の土地投資は30日目の収益に寄与する」といった判断を強い既存方策と比較する層とは異なる。最終A2ソースが不足しているため完全な不在証明はしないが、保存評価における戦略的plan介入は確認できない。

さらに103,922件のraw→mask変更のうち98,555件は移動になり、そのうち65,180件は元のrawが非移動・非PASSの作業だった。例えば「ここではWATERできないのでEAST」「HARVESTできないのでWEST」という形である。これはmaskが誤りだという意味ではない。**作業の対象・目的地を保持しないまま、実行不能な作業要求が移動へ置き換わる構造**が大量にある、という意味である。移動先で何を終えるかまで制御しなければ、合法な移動は増えても経済が回るとは限らない。

## 5. 83%というaccuracyが隠していたもの

以下は保存された旧test＝開発診断データを、今回保存重みで再推論した値である。未使用のfresh holdoutではない。また教師状態でのraw予測一致率であり、実戦の仕事の成功率ではない。

| 対象 | 正解/対象数 | 一致率 |
|---|---:|---:|
| actor token全体 | 13,899/16,692 | 83.27% |
| 非移動・非PASSの作業token | 13,402/14,967 | 89.54% |
| NORTH/SOUTH/EAST/WEST | 490/1,697 | 28.87% |
| market token全体 | 4,617/6,714 | 68.77% |
| EOS＋HIRE | 3,642/4,028 | 90.42% |
| EOS/HIRE以外の経済判断 | 975/2,686 | 36.30% |
| SELL系 | 477/1,615 | 29.54% |

actorデータは作業を保持し、MOVE/PASSを1/8で抽出している。評価集合も作業に偏る。そのため「作業tokenを言い当てる」能力が全体値を押し上げ、移動の弱さが目立たなくなる。marketでも、EOSとHIREを除くと一致率は大きく下がる。EOS/HIRE以外の2,686行のうち1,071行ではEOSが予測されていた。

低い移動一致率だけで、すべての違う方向が戦略的に誤りだとは言えない。代替経路もあり得る。ただし、この教師状態での弱さと、次節の実戦での移動偏重・生産消失が同時に観測されている。**運搬や対象選択を十分に扱えていない、という仮説を優先検証する根拠は強い。** モデル容量だけが原因、間引きだけが原因、あるいは特徴表現だけが原因とはまだ分離できていない。

最小の純粋学習側の切り分けは、同じ20 episode・同じモデル・同じdecoderで、MOVE/PASSの抽出率と損失重みだけを変更する実験である。これは主役の競技用ハイブリッド実装とは別に行う。

## 6. 何が経済を壊しているか

64試合でA2が発行したactor commandは306,692件、うち移動269,847件、87.99%である。同じ試合の相手側は42.35%だった。非移動・非PASS作業はA2が11.63%、相手が50.54%。人数や戦略が違うので、その差を単独の因果効果とは解釈しない。

直前の移動をすぐ逆に戻る動作はA2が平均164.25回/試合、相手が12.53回/試合だった。正常な往復も含まれ得るため全件を無駄とは断定しないが、仕事の未完了・目標切替と結び付けて調べる価値がある。

平均の農場状態は次のとおり。dayはリプレイのゼロ始まり値であり、record192がday=8、record480がday=20である。

| 状態 | A2現金 | 相手現金 | A2土地/相手土地 | A2作物/相手作物 | A2家畜/相手家畜 |
|---|---:|---:|---:|---:|---:|
| day=8 | 1,452.53 | 650.81 | 1.00 / 2.00 | 9.47 / 37.00 | 2.22 / 10.00 |
| day=20 | 9,634.17 | 66,253.52 | 1.20 / 3.09 | 0.63 / 58.94 | 0.16 / 16.81 |
| 終局 | 9,604.55 | 157,465.67 | 1.25 / 3.09 | 0.03 / 0.94 | 0.00 / 16.52 |

day=20に48/64試合が作物・家畜ともゼロ、終局には62/64試合が両方ゼロ、家畜は64/64試合でゼロだった。終了時の土地が1区画のままの試合は48/64。逆に、空の牧草地はday=20に平均24.48マス、終局には26.36マスあった。BUILD_PASTUREはA2が2,537回、相手が934回だった。

終局の作物が少ないこと自体は、収穫して換金し終えた正常な結果でもある。問題は**day=20時点で既に生産がほぼなく、その後も資金が伸びない**ことである。相手の終局作物の少なさと同じ意味にはできない。またanimal exitを全部バグ扱いもしない。

非常に重要なのは、day=8のA2は相手より現金が多い点である。それでも相手は土地・作物・家畜に再投資している。**直近の現金を増やす行動を「ロジックの方が良い」と判定すると、まさにこの負け方を強化しかねない。** 比較対象は最終資金差と、その途中で維持すべき生産能力・労働・運搬・資源制約である。

改善対象は少なくとも「準備→移動→作業→回収→運搬→販売→次の生産投資」という連鎖である。終盤のSELLだけを付け足しても、20日目までに失った生産収益は取り戻せない。

## 7. 「100%」の正しい読み方と残る監査項目

添付REPORTの100%は教師模倣accuracyではなく、発行された非移動・非PASS作業について、固定engineで直後に効果を認めた割合である。A2の記載は35,683/35,683で、別途day-boundary/terminal UNKNOWN 730との記載がある。

これは「必要な作業を選べた」「畑を維持できた」「資金を生んだ」「相手より儲かった」のどれとも同義ではない。不要な牧草地の増設でも、建設の効果が発生すれば一手効果の指標は成功になり得る。

今回はengineがないため、この専用effect監査を独立実行していない。古いinline traceのeffect検査では、OBSERVED 44,096 turn、work row34,951、success34,466、UNKNOWN_DAY_BOUNDARY1,856 turn、PENDING64 turnという別集計もある。これは計測方法と単位が違い、専用監査の否定証拠とはならない。ただし、専用監査35,683と発行work総数35,683の一致、UNKNOWN730の扱いは、次回必ずaction ID単位で対応表を出し、checked/success/failure/unknownと分母を明確にすべきである。

## 8. ポケモン側で実際に有効なハイブリッド

### 8.1 モデルは、何でも直接生成するのではない

`ml_runtime.py` はengineが提示する `select.option` から候補を取り、状態と各候補の特徴を組にして採点する。意味的な候補重複も除く。保存モデルはLightGBM形式、2,000 trees、823特徴である。

ただし、このモデル形式自体を勝因と断定する材料はない。今回参考にすべき第一の違いは、**実行可能な候補を前提にしたランキング問題へ整理されていること**である。

### 8.2 モデルへ任せる場面を限定している

`Ranker.is_scorable` は、許可されたcontext、単一選択、候補数などを確認する。学習が適すると評価されたcontextだけでモデルを使い、対応外や特徴/採点失敗時はルールへ戻る。export metadataの最小support400・最小context top1 0.6は、contextを採用する設定であり、「毎回勝率60%以上ならモデル」というゲートではない。

### 8.3 限定された補正がモデル選択を変更する

`main._choose` はルール候補も計算し、対応場面ではrankerを使い、そのあと `Planner.adjust` がボス対象、回復元、エネルギー配分、攻撃可能性等の狭い条件を確認する。補正条件内の候補をモデルscoreで選ぶ処理もある。すべての上書きが長期的な優越を数学的に保証するわけではない。

モデルが選んだ候補ではなく、最終的に実行した選択を `commit` / `observe_external` / `note` で履歴へ反映する。これは農場側にも重要な設計である。ルールが上書きしたのに、モデルの記憶だけが「元の作業をした」と進む不整合を避けられる。

### 8.4 探索はOFFだった

`turn_search.py:53` は `ENABLED = False`。`build()` はこの場合 `None` を返す。`main.py` の冒頭説明や実装中に探索・手順継続が存在しても、添付最終版の既定動作では有効でない。

ソースコメントには、当該ターンのprize獲得を優先する探索が局所的には多く取れる一方、対戦成績は悪化したとの開発者記録がある。openingのみ0.478、手順完遂0.344などの数字が書かれているが、対応する生リプレイは添付されていないため、今回独立検証済みの勝率とは扱わない。

ここからの教訓は、「探索＋手順継続を移植すれば強くなる」ではなく、**短期指標が良い上書きでも全体を弱くするなら無効化する**ことである。タスク継続は必要な実行設計になり得るが、悪い目標に忠実になるだけでは勝てない。

なお、ユーザーが経験したML版の強さを否定するものではない。この添付だけでは、その強さの何割がモデル、ルール、補正に由来するかを因果分解する対戦記録までは確認できない。

## 9. 推奨する次のアーキテクチャ

### 9.1 競技用と研究用を分ける

**競技用**：改変しない強いv122/v124を対照として保持し、候補タスク選択への学習寄与を測る。少なくとも既存の強さを失わない出発点を作る。最初の基準は版番号で決めず、利用可能な固定環境で同条件評価し、事前に決めた指標で固定する。v123は追加評価しない限り独立familyとして数えない。

**研究用**：A2の純粋BCを残し、移動抽出率、task/target/history、encoder、データ数の変更を一つずつ調べる。研究版が弱い限り競技版を弱いA2へ戻す必要はない。

これは「v124が上限」という方針ではない。候補をv124の現在の一手だけに制限すれば上限が固定される。上位ログ由来の異なる投資・配置・維持・回収計画を候補に加え、良いものを選択できる余地は残す。ただし、最初から全部を入れず、一つの新しい判断能力ごとに検証する。

### 9.2 方角でなく、仕事を選ぶ

例として、次のような単位を扱う。

```
FEED_TASK: actor / target animal / feed source / quantity / deadline
HARVEST_DELIVER: actor / crop target / maturity / capacity / destination
REPLANT_TASK: actor / tile / crop / seeds / water / expected completion
INVESTMENT_PLAN: land or animal / funding / future labor and maintenance
MARKET_PLAN: sellable surplus / protected feed and seed / order prefix
```

候補は提案であり、現行実装に存在するAPI名ではない。最初に全種を実装するのではなく、baselineの実測損失を調べ、**一つのタスク系統**を選ぶ。

候補生成器は、強いbaseline案、継続中のtask、許可された新task、何もしない安全な選択肢などを返す。モデルは状態と候補の組を採点する。選ばれたtaskはロジックが目的地までの移動、必要品取得、実作業、搬入、完了確認を扱う。同turnの複数actorは共通ledgerで資源予約し、互いに矛盾しないよう選ぶ。

taskには開始条件、所有actor、予約資源、期限、成功条件、失敗条件、再計画条件、baselineへ戻る条件を持たせる。途中でただ戻すと古い固定手順と現在の状態が食い違うため、**実状態から再計画可能かを先に確認する**。

### 9.3 ルールで上書きする理由を分ける

第一は実行不能・二重予約などの契約違反。これは棄却すべきだが、合法性を収益性と呼ばない。

第二は、限られた前提で明確に比較できる事柄。例えば同じ仕事を実現する二経路の到着時間比較。ただし時間帯・衝突・同turn相互作用まで前提に入れる。

第三は、中長期収益の優劣。ここでは単なるsoftmaxの最大確率や「今いくら売れるか」ではなく、同条件でのbaseline案との分岐評価や、検証したcontext別増分効果を使う。不確実な場面でbaselineへ戻すのは設計案であって、任意のfallbackが理論的に安全だという意味ではない。

現金だけの短期searchは避ける。最終資金差を目的とし、途中の評価補助に稼働作物、動物維持、回収期限、運搬能力、労働需要、確保済み餌・種・現金を使う。生産能力の指標を機械的な報酬にすると無駄な増設も起こり得るので、最終成績と整合するかを検証する。

## 10. 学習の次の使い方

最初は教師模倣で候補順位の初期化を行う。ただし、一つの時刻の全actor joint actionを無理に分類するより、対象・仕事・必要資源・完了までの構造を揃える。候補集合に教師の仕事がない場合は、モデル不正解ではなく**候補欠落**として別集計する。

次に、実行した候補がbaseline案より最終資金差を改善するかを学ぶ。offline分岐評価では、同じ初期状態、同じ相手方策、適切な乱数対応で候補を比較する。相手が実際に応答する方策を使い、未来の相手action tapeをそのまま答えにしてはいけない。完全engine stateを使う評価器と、許可されたobservationだけを見る方策を分離する。実行時の特徴に相手private、未来価格、未来action、終局結果を混ぜない。

学習器自身が到達した失敗状態へ、その状態に適した教師・plannerのラベルをつけて再学習する必要がある。元教師の「同じ時刻のaction」を貼り付ける方法は避ける。Round9の回復ラベル3件は記録上まだ学習に使われておらず、実装済みDAggerではない。

MLPをLightGBMに替える実験は可能だが、ポケモンで使われているから強いとはいえない。候補集合、特徴、学習行、目的関数を揃えた比較として行う。モデルの複雑化とデータ増量を同時に進める前に、問題の単位を整える。

## 11. 次の実装順序と判定

### Phase A：baselineと実行契約を固定する

ローカルにある最終A2 v3ソース・提出物・engine・v122/v124をhashで特定する。baseline無改変版とハイブリッドwrapperの強制baselineモードを比較し、全action/stateが一致することを確認する。モデルが読み込まれなくても静かにbaselineで勝って「学習成功」と報告することを禁止する。

### Phase B：一つのタスク系統だけで比較する

保存ログとbaseline自身の失敗例から最初のtaskを選ぶ。A2が苦手というだけで、v124もそのtaskで改善余地があるとは限らない。候補集合・実行器を固定し、ルール順位付けと学習順位付けを比較する。最初の実験から土地、家畜、販売、crop mixを一斉変更しない。

タスク単位で、候補存在率、選択の質、完了率、完了時間、同turn競合、予約解放、baseline復帰、最終資金への寄与を出す。「model called」の回数ではなく「モデルが何を変更したか」を記録する。

### Phase C：閉ループ改善を測る

同seed、同相手、両seatでbaseline、同候補ルールranker、同候補学習ranker、必要ならゲート付き版を比較する。A2は参考対照であり、A2より強いだけでは採用しない。

既に使った16 seed×2相手×2 seatは開発用。信頼区間はseed単位のブロックを保ち、64独立Bernoulli扱いをしない。候補の選択や閾値調整後に、未使用の最終確認範囲を一度だけ開く。勝率、差額、絶対資金、family別・seat別、計算時間、重大不具合を事前定義する。最終判定の主指標を結果を見て切り替えない。

### Phase D：通過後だけ能力を広げる

有意義な増分が確認できたtaskから適用領域を広げる。次に投資、作付け構成、雇用、土地拡張など、強いbaselineを超える戦略選択を加える。データ数増加、encoder変更、大規模探索は各々独立した比較にする。改善がない場合は追加を取り消し、失敗を報告する。

## 12. 最終判断

今回のRound9を「学習が動いていない」と片付けるのは誤りである。しかし、「学習が適切に進んでいるから、同じ形式のまま規模を増やせば勝てる」とする根拠もない。

現状で最も改善余地が大きいのは、**primitive action分類を経済的に完結する意思決定へ変え、モデルの選択能力とロジックの実行能力を分担すること**である。その際、強い既存方策を対照として残し、実際の最終成績を改善したかを測る。

ポケモンから移すべきなのは、ゲーム固有のロジックやOFFの探索ではなく、候補化、適用場面の限定、実行履歴の整合、限定補正、悪化した機能の無効化という設計原則である。これでレート2000/3000を保証できるわけではないが、弱い独立BCの改善だけを繰り返すより、今回の証拠に沿った次の検証になる。
