## 7. 学習を行うときの対象と対照

Round10は72教師・12相手×seed group、test18件中positive1。検証損失の最良記録はepoch40付近、600まで進めると悪化。常時negative精度94.44%に対してモデル88.89%。旧モデルをそのまま長く回すことを主要作業にしない。

まず、実行可能な候補が結果を変える状態を作る。KEEPを必ず含め、同じ到達状態からcandidateとbaselineを分け、相手も反応する終局結果を取得する。実行前提不成立、実行成立だが不利、同値、改善を別ラベルにする。

候補への学習目標は「上位者の行動名」だけではなく、その候補を自分の状態で使った価値。相手予測モデルなら1/2/4ターン別の校正、数量誤差、イベント基準の適合率、打切り観測を評価する。学習による方策変更なら得点差・勝敗遷移・行動変更数を評価する。

最初は単純な規則／小モデルとの対照を置く。モデルに渡す候補集合、実行器、後処理をそろえる。モデルだけが使えない候補を選び、規則だけが安全な候補を使う比較にしない。未来の店舗、真のseed、相手のprivate、episode ID、将来の勝敗は実戦の特徴に入れない。

訓練／検証／最終評価は行単位で混ぜず、episode、world seed、source lineageと時点で分ける。同じ世界の両seatを別splitへ置かない。重複したpublic sourceの大量行で多様性を水増ししない。

データが足りない場合は候補の有効な介入データを増やす。モデル大型化だけで解決しようとしない。反対に小さな無効果候補が失敗しただけで学習全体を断念しない。実施した訓練更新数、保存hash、別プロセスでのロード、推論数、候補選択数、最終行動差分数を必ず記録する。

## 8. 評価・組合せ・採用

主要指標は1勝=1、引き分け=0.5、敗戦=0の得点。基準と同じ相手・seed・seatで比較し、負→勝、勝→負、分→勝／負を分ける。自資金差・相手資金差・margin差も記録するが、平均marginだけで採用しない。

AとBの単独改良が見つかったら、BASE、BASE+A、BASE+B、BASE+A+Bの2×2比較をする。生産・市場・台帳の各変更が本当に発火したか、どの順番で適用したかも記録する。今回のようにBが変更0なら、組合せの相互作用が解決したとは言わない。

新しい原版も、元作者の版と変更版を別々に保存する。土台が変わればoverlayの効果を再検証する。B1上の正例を別方策への因果証拠に転用しない。

開発集合で候補を選び、コード・閾値・相手セット・指標を固定してから新しいseedのholdoutへ進む。初期案は24～32独立seed、実行できる独立性の高い複数相手、両seat。これは実験予算案であり、結果を見て都合よく標本数や基準を変えない。必要予算が不足ならINCONCLUSIVEとする。

seed単位にまとめて不確実性を評価する。すべての試合を独立として狭い区間を出さない。重要相手群ごとの悪化と、現在metaへの得点改善の両方を見て、事前に許容幅を決める。「新しい負けが1件でもあれば必ず棄却」という絶対基準だけにはしないが、実行不具合や巨大な重要相手の退化を平均で隠さない。

同じseedの両armで店舗列が同じとは限らない。盤面が乱数消費を変える仕様を考慮し、通常環境の総合効果として評価する。店舗を固定した改造環境は診断専用で、公式環境の改善証拠に混ぜない。

最新上位のrawが取得できる場合は実物とhashを保存する。CSVのreplays_availableを取得済みraw数としない。相手のコードがなければ、行動固定再生・学習した代理・本物の反応する方策を明確に別区分にする。

## 9. 提出互換性と完全な成果物

既知の提出成功基準はRound10 B1。以前のfixed_v2ではmain.py最後の診断関数が誤選択された。最終entry以降に別callableを置いてローダーの選択を壊さない。import smokeだけでなく、最終tarから公式ソースローダーを使う。

最終archiveのmain.py、モデル、依存物のhashが実際に評価したものと一致すること。空のexec環境、相対import、__file__、圧縮埋込、標準ライブラリのみの条件、複数独立agentインスタンスの状態分離を確認する。新規候補で720状態・719判断、終端status、エラー、時間／メモリ、注文上限を検査する。

baselineを呼んだだけなのに「学習版」と命名しない。採用できる候補がない場合も、B1維持、確認した負の証拠、次の具体的な探索対象を成果として残す。

最終的に次の一式を作る。

| 成果物 | 必須内容 |
|---|---|
| REPORT_JA.md / FINAL_STATUS.json | 実行したこと、未実行、候補の判定、採用理由、限界 |
| SOURCE_REGISTRY.json | 原典、版、取得時刻、hash、実際の実行entryと設定 |
| ARM_REGISTRY.json / EFFECTIVE_DIFFS | 何を変更し、どこで発火し、最終行動が何回変わったか |
| 実験protocol・coverage | 対戦前の条件、全予定セル、欠落・例外、data split |
| GAME_RESULTS・PAIRED_RESULTS | 両者現金、得点、勝敗遷移、相手・seed・seat |
| SOURCE/ENGINE/AGENT HASHES | 実物ファイルの存在とハッシュを検算 |
| 学習をした場合のMODEL_USAGE | 訓練更新、重み、再読込、推論、選択、行動変更 |
| 代表例・rawリプレイ | 良化、悪化、無効果、相手反応、生産差、価格差の事例 |
| REPRODUCE.md | 実在するスクリプトを同梱した再実行手順 |
| Candidate archive | 本当に採用ゲートを通った実物だけ。無承認で提出しない |
| 最終ZIPとmanifest | 必要コード、設定、モデル、比較結果、ログ、ライセンス。存在しないファイルへの参照で済ませない |

「学習が終わった」「テストが通った」「平均現金が上がった」で結論を終えない。どの基準を、どの相手と世界に対して、どれだけ上回ったか。上回らなかった場合は、候補不足・実行不成立・予測誤差・価値判断・汎化のどこに問題が残ったかを、実物から説明する。

この依頼は計画書だけの作成ではない。手元の実物を確認し、公開候補の取得、実装、対照を含む実行、結果の記録まで進める。外部取得や資源が制限された場合は、できた工程を完了し、その境界を明記する。
